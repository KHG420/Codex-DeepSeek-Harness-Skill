# Codex 规划 → dsh 执行 → Codex 验收

Codex 是任务负责人和验收者，DeepSeek Harness 是实现者。保持本轮任务活跃，直到实际通过验收或确有外部阻塞。dsh 返回 0 仅表示模型回合完成，不代表实现成功。

## 开始前

- 先确认 `command -v dsh`、`dsh --version` 和 `dsh --profile headless --help`。首次使用、运行报错或凭证/模型变化时，按 [local-runtime.md](references/local-runtime.md) 排查并做最小真实调用。已验证的环境不必每个任务重复付费探测。
- 阅读当前项目适用的 `AGENTS.md`，把影响执行的约束显式写入任务单；dsh 不继承 Codex 对话、工具、权限或已读 skill。
- 查看项目必须先用 codegraph MCP 或 CLI。不可用先尝试 `codegraph init`；确实失败才回退到基本工具。记录新建的 `.codegraph/`，不要把索引纳入产品提交。
- 为 dsh 核实本任务需要的工具入口与工作目录，按 [handoff.md](references/handoff.md) 的“工具与检索策略”交接。优先使用已有 CLI；Codex 的 MCP、连接器和登录授权不会自动传给 dsh。配置中存在工具不等于实际调用已验证，不为补齐工具目录安装或启用无关插件。
- 检查 Git 分支、HEAD 和工作区状态。干净仓库默认新建 `codex/<task-id>` 分支的独立 worktree，核实其中能运行项目环境。存在用户未提交修改时保留它们：与任务无关则从 HEAD 隔离；与任务相关则用当前工作区并记录基线，不能假装新 worktree 含有这些修改。
- 一次只有一个代理写同一工作区。运行助手只约束同助手的并发调用；Codex 和其他工具仍须主动遵守。验收时 dsh 必须已停止。
- 不默认修改全局模型、权限或密钥，不把启动失败自动转成放宽权限。继承用户既有配置，明确任务可写范围。工作目录和提示词约束不等于 OS 沙箱。
- 实测本任务需要的解释器/依赖和测试基线，不凭路径推断依赖已安装。用下述 `record` 留下版本/依赖探测与必要测试的真实输出；在任务单引用可用环境和历史失败。相同环境与基线未变时复用证据；历史失败须比对位置和原因，不能掩盖新增失败。

## 1. Codex 调查并冻结任务

修 bug 先复现或追踪根因，再给实现方案。新功能先明确触发场景、预期行为、接口限制和现有实现模式。

在项目外创建任务目录（例如 `$CODEX_HOME/dsh-tasks/<task-id>/`，未设置时使用 `~/.codex/dsh-tasks/`）。按 [handoff.md](references/handoff.md) 编写 `task.md`，包含目标、基准 HEAD、原有修改、允许范围、禁止事项、事实与假设、编号验收条件、验证命令和实现建议。

任务单以已确认事实、最小改动范围和可观察验收条件为主，不重复抄写整份 skill。数值/分支任务用短矩阵分别说明正常值、零值、缺失、非法输入和合法负结果；交接前准备关键正例与反例（必要时写成测试），不得把它们留到返修才补。测试输入自身要满足既定模型前提。

将会被本轮读取的外部测试、fixture、overlay及其实际依赖逐个通过 `--input` 登记；输入原路径和快照都冻结，运行器在执行结束及 `check` 时校验。不能在 dsh 运行中原地修改它们，即使修改者是 Codex；新增独立测试使用新版本文件、在当前写入停止后另行验收，交给返修时登记到新 attempt。不自动递归解析 overlay 依赖，由任务负责人列全。

验收覆盖核心行为、相关回归和改动范围，区分硬约束与建议。不要用计划完成、编译通过或模型自述替代行为验收。小任务保持一个任务单；多实例并行已搁置，不启用。

## 2. 调用 dsh 实现与自测

用本 skill 的 `scripts/dsh_run.py`，传绝对路径：

```sh
python3 <skill目录>/scripts/dsh_run.py run \
  --workspace <Git工作区根目录> \
  --task <任务目录>/task.md \
  --output <任务目录>/attempt-01 \
  --capture <允许修改的相对文件或目录> \
  --input <外部验收文件绝对路径> \
  --timeout 900
```

`--capture` / `--input` 可重复；没有外部验收文件就省略 `--input`。显式选择经审查的源码范围，不选择仓库根、凭证或大数据目录；单文件上限 2 MiB，每轮前/后各 20 MiB，超限先缩小范围或另定专项取证，不静默跳过。选择范围内的 Git 可见文件保留内容（链接只存目标字符串，不跟随），忽略文件不自动复制。新文件所在范围也须事先选择。范围外变化仍记录哈希和路径，不代表已审查；没有任何 `--capture` 时只有变化清单，不能假称完整 diff。详见 [handoff.md](references/handoff.md)。

使用参数数组或正确 shell 引号，不把任务内容拼成 shell 命令。助手保存任务副本、执行报告、stderr、退出码、前后摘要和本轮增量 diff。证据目录权限为 0700，但没有自动识别所有秘密的能力。每次使用新 attempt，不覆盖历史证据。

`--timeout` 是单次执行上限。适度轮询状态，按实际阶段/证据汇报，区分实现者自述、自测与独立验收；没有变化就简短说明仍在执行，不反复宣称“马上完成”。Headless 可能仅结束时输出最终答案，短时间无 stdout 不等于卡死。避免反复读取长推理日志来制造进展。

实现者读项目规则、最小化改动、执行指定验证，不提交、推送、部署、改凭证或自行委派。报告由 stdout 保存为 `execution.md`，不要求 dsh 写工作区外的报告。Codex 根据事实负责修订任务，不能让 dsh 降低验收标准。

`EXECUTED`、`EXECUTION_FAILED`、`TIMED_OUT`、`INTERRUPTED`、`LAUNCH_FAILED`、`EVIDENCE_FAILED` 都不是验收结论。失败先检查实际 stderr、报告和文件，再决定局部返修、重新规划或外部阻塞，不无证据重跑或换模型。

## 3. Codex 独立验收

先从原始任务单重建验收清单，再看实现与执行报告。当前 Codex 直接验收；必要且委派已获授权时，可用独立 Codex 会话做有界审查，主会话仍须确认实际验证。

1. 阅读 `result.json`，确认 dsh 已停止且执行证据完整。
2. 检查 `delta.json` 全部变化及 `changes.patch` 的本轮 before→after 差异，不把原有脏改动算成本次修改。新增、删除、模式和链接变化均在清单中；二进制原文在 `blobs/`。`content_captured=false` 表示只有哈希，必须补充范围审查，必要时从可证明基线重新执行，不能推定安全。旧 attempt 的 HEAD 差异格式保持原样，不按新格式误读。
3. 检查根因、行为、相关回归、测试有效性和范围。测试被删除、跳过、弱化或用 mock 掩盖核心问题都不能算通过。
4. Codex 自己运行最小相关验证，用 `record --candidate <attempt>` 记录真实命令、退出码、stdout/stderr、候选前后指纹；`review.md` 引用各条记录。不要手工回忆或改写日志充当原始证据。实现者自测不能代替独立验收；同一候选/输入/环境上已完成的同一检查无需反复运行，代码/输入/环境变化后重跑受影响检查。关键环境缺失就是未验证。
5. 验证前后均运行 `dsh_run.py check --output <attempt目录>`。它只核对代码和任务未漂移，不检查业务正确性，不生成 PASS。
6. 按 [handoff.md](references/handoff.md) 写 `review.md`，记录候选 fingerprint、任务摘要、AC 逐项结果、验证证据和结论。

指纹覆盖 HEAD、暂存区和所有 tracked / 非 ignored untracked 文件的内容、模式和符号链接；`--input` 补充登记的外部/忽略验收文件。它不冻结系统环境、数据库或外部服务，也不是持续监控或 OS 只读锁；其余依赖需专项验证。助手不支持 submodule 条目，需先确定取证方式，不绕过失败声明整体通过。

验证工具若重写 tracked 文件，先调查差异；有意义的代码变更交回 dsh 重做验收。只恢复确由本次验证生成且已确认不需要的变化，不批量 reset/clean。通过后的提交或代码变化也使候选检查失效，需复核并记录新版本。

## 4. 返修与结束

- `PASS`：全部必要 AC 满足，独立验证完成，范围合适，无未解决实质问题，最后一次候选检查通过。明确可用工作区和证据位置，不把 PASS 扩展为发布授权。
- `REWORK`：按编号写具体位置、证据、实际与预期、对应 AC 和验证方式。保持原任务单，使用 `--feedback <attempt-01>/review.md --output <attempt-02>` 交回同一工作区。每次 headless 是新会话，输入必须自包含；复验修复和受影响回归。
- `BLOCKED`：只有缺少必要用户信息、凭证、权限、外部服务或超范围决策时使用，写明证据、剩余 AC 和解除条件。代码错误或复杂度本身不是阻塞。

同一问题两轮返修仍未解决，切回 Codex 重新调查根因并修订任务单，保留旧版本；不继续相同提示词的无效循环。有新的可验证方案时继续推进。涉及项目规则要求确认的依赖、API、持久化数据、架构或范围扩展时，先完成可审查方案再提出必要确认。

最终说明实现、关键验证、结论、交付位置和真实限制。不要以“计划好了”“dsh 已结束”或“还可以继续”结束未完成任务。

## 执行中持续改进本 skill

后续优化或讨论并行实现时，读取 [改进待办与并发设计备忘](references/improvement-backlog.md)。其中未实施的提案不改变本 skill 的现行执行规则，也不授权自动启动多个实例。

在用户已授权优化本 skill 的会话中，发现有实际证据支持、能够改善后续执行的地方，Codex 可以优化本 skill 的说明、交接约定和配套脚本。安装本 skill 本身不代表授予修改它的权限。原开发任务仍是主线；完成必要优化后继续执行与验收，不以优化 skill 代替交付。

- 先定位真实流程问题，例如交接缺少必要上下文、指令歧义、重复无效操作、运行助手缺陷或验收遗漏。根据复现、日志、实际 diff 或验证结果做最小修正，不把猜测和一次性的项目细节扩写成通用规则；本机特例写入相应运行参考。
- 由 Codex 修改本 skill。dsh 发现流程问题时，在执行报告中提供现象、证据和建议；这不授予 dsh 修改工作区外 skill 的权限，也不解除当前任务的范围限制。
- 改说明时检查一致性、引用和 skill 格式；改脚本时先复现问题，补充最小相关回归验证并运行受影响检查。验证失败则修正或撤销本次优化，不留下半成品。
- 不在 dsh 运行期间改变它正在使用的执行脚本或本轮约定；在交接边界应用更新。已经开始的 attempt 保留原任务、提示词和证据，需要改变执行约定时创建新 attempt，并把相关更新明确传给 dsh。
- 不通过优化降低验收标准、跳过检查、放宽权限或抹去失败记录。涉及新生产依赖、外部系统、公共接口、持久化数据或明显扩大的架构变更，仍遵守用户和项目原有确认边界。
- 在当前任务记录中简述触发现象、skill 改动及验证结果，最终答复简要披露。没有值得固化的发现就不修改，也不额外建立优化日志体系。
